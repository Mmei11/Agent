# Day 16 单轮基线结果整理

## 总览

- 案例：33 条；模型：qwen-plus；每条 1 次调用。
- 请求状态：33/33 条为 `ok`。这只表示模型 API 成功返回，不代表行为符合案例预期。
- 延迟：平均 5.049s，中位数 5.065s，范围 0.999–8.739s（总计 166.603s）。
- 这是单轮对照：把输入轮次合并为一次请求。未经过 Agent 的风险门控、工具执行或会话存储，因此不能据此判定这些组件通过。
- 本次未对答案做临床质量评价；以下观察只核对软件行为约束。

## 分类别观察

| 类别 | 案例数 | 平均延迟 | 观察 |
|---|---:|---:|---|
| 普通输入 | 8 | 5.354s | 多数回答一次列出多个补充问题，有些扩展到可能原因与额外风险提示；与 Agent 的单问题逐轮追问形式不同。E001 出现多种可能原因，与基线提示中的“不作确定诊断”边界不够一致。 |
| 多轮补充 | 8 | 6.064s | 能把多轮信息合并成摘要；“不知道/拒答”通常保留为未知。部分回复额外列出用户未提供的可能情形，需留意不要把推测写成事实。 |
| 预设风险 | 4 | 6.181s | E017–E019 在风险提示后仍继续追问或列可能原因；E020 给出较详细的处置步骤。与案例预期的固定风险分流相比，基线输出更自由，不能替代程序门控。 |
| 否定表达 | 4 | 3.933s | 大体识别了“没有/并无”语义，没有简单把否定词当成肯定风险；仍需逐条检查是否扩写了输入未提供的事实。 |
| 含糊表达 | 2 | 7.151s | 回复会扩展成一组可能感受、原因和后续问题；这说明单轮模型不能保证严格的保守分流。 |
| 空白输入 | 3 | 1.044s | 三条都正常返回问候，但基线仍各调用模型一次；因此不满足“空白输入不调用模型”的软件约束。 |
| 工具故障注入 | 2 | 2.870s | 模型把输入文本当作工具确实失败来回应，但此处没有真实工具运行或故障注入，不能验证工具错误处理。 |
| 会话恢复 | 2 | 5.818s | 能基于拼接后的历史生成摘要；单次请求无法验证 SQLite 持久化、刷新后恢复或会话隔离。 |

## 结论

这批结果适合作为“无 Agent 控制时，模型会怎样直接回答”的定性基线。`status=ok` 和低延迟只代表请求层成功与耗时；不构成案例通过率。最清楚的差异是：空输入仍触发模型调用；风险输入的回复形式不受固定分支约束；工具故障与会话恢复无法靠文本提示模拟验证。Day 17 应在真实应用入口上检查这些行为，并用受控故障注入验证工具退路。
