# 优化阶段指标定义与基线（Phase 0）

> 建立日期：2026-10-23
> 对应版本：v0.1.0（Day 20 交付版）
> 目的：让后续每一个改动都能回答"哪个数字应该变、变了吗"
> 数据均为本机实测，测量命令见文末；不涉及真实患者数据。

---

## 0. 为什么先定指标

优化阶段最大的陷阱是"改了很多，但说不清有没有变好"。选指标遵守三条原则：

1. **可行动**：指标下降时，能指向具体模块。比如"抽取 F1"能指向 `intake.py`；"用户满意度"不能。
2. **敏感**：改了相关代码，指标应该动。如果一个指标在你改完 prompt 后纹丝不动，它要么太粗、要么测的不是这件事。
3. **抗投机**：指标不能靠"针对测试集打补丁"刷高。所以每个质量指标都要有 **dev / holdout 划分**，只看 holdout 的泛化表现。

三条落地规则：

- **硬约束用代码断言，质量用打分，效率用计量。** 三者分开报告，不混成一个分数。
- **没有基线的指标不许进入下一阶段。**
- **单个分数没有意义，必须带样本量和波动范围。**

---

## 1. 指标分层

| 层级 | 性质 | 处理方式 | 例子 |
| --- | --- | --- | --- |
| 硬约束 | 出现即失败，不可接受概率性 | 代码断言，CI 阻断 | 风险路径不得进入普通决策节点 |
| 质量 | 连续、有波动 | judge 打分 / F1，多次采样 | 抽取准确率、追问相关性 |
| 效率 | 计量 | 分位数 + 成本核算 | p95 延迟、每会话 token |

## 2. 五个北极星指标

### M1｜字段抽取槽位 F1（质量 · 代表"理解用户"的能力）

**定义**：在 30 条人工标注样本上，对 9 个字段逐槽位判断"系统是否提取到该字段"，计算 micro-F1。必需字段 6 个（主要症状/持续时间/部位/程度/伴随表现/已知背景）；可选字段 3 个（加重缓解因素/时间模式/测量值，用户提到才提取，不主动追问）。

**公式**
```
TP = 期望有该字段 且 系统提取到
FP = 期望没有     但 系统提取到
FN = 期望有       但 系统没提取
precision = TP/(TP+FP)   recall = TP/(TP+FN)   F1 = 2PR/(P+R)
```

**为什么用"槽位级"而不是"值完全一致"**：值一致会惩罚合理改写（"两天" vs "2 天"），让指标噪声大于信号。槽位级回答的是"该问的信息，系统知不知道"。值的正确性作为**附加检查**：提取到的值必须包含标注里的原文片段，否则记为错误。

**样本**：[eval/probes/intake_samples.jsonl](../../eval/probes/intake_samples.jsonl)（30 条虚构表达）
**标注规则**（必须按此填，否则指标不可比）：

1. 每个字段填**消息里逐字出现**的片段，不要填推断结果。例："从前天开始，脑袋嗡嗡的" → 主要症状填 `["脑袋嗡嗡的"]`，持续时间填 `["前天"]`。
2. **否定不算提取**。"没有发热"不填伴随表现；"没有呼吸困难"不填主要症状。
3. 用户拒答或无法描述（"我不太想说我哪里不舒服"）→ `expected` 留空 `{}`。
4. 含糊时间照抄原文。"有一阵子了" → 持续时间填 `["有一阵子了"]`。
5. 一条消息命中多个字段就都填，一个字段有多个片段就都列。
6. 填完把该行 `labeled` 改为 `true`。

**补充约定**（同一句话在不同日子标出不同结果，F1 就变成噪声，所以先把这几条定死）：

- **取最短完整原文片段**，不归一化、不解释。"已经三天了" → `["三天"]`，不要写 `["3天"]`。
- **程度只描述主要症状**；伴随症状连同修饰词一起放进"伴随表现"。"咳嗽，有点发热" → 主要症状 `["咳嗽"]`、伴随表现 `["有点发热"]`，程度留空。
- **否定词和被否定的内容都不填**。"没有发热" → 伴随表现不填。
- **没有专属字段的描述**（频次、节律、诱因）放进最接近的字段；拿不准就放主要症状，并在该行加一个 `"note"` 字段写清理由。`note` 不参与打分，只留作复核。
- **可选字段的归属**（2026-10-25 起）：`加重缓解因素` = 什么让它变重/变轻（"站起来更明显""弯腰的时候更疼""爬两层楼就喘"）；`时间模式` = 发作规律与频次（"一阵一阵""晚上更疼""拉了四五次"）；`测量值` = 体温、血压等数值（"三十八度五"）。起病时间（"今天早上开始的"）属于**持续时间**，不属于时间模式。
- 用户拒答、无法描述、只说背景 → `expected` 留空 `{}`，但 `labeled` 仍要置 `true`（这和"没标"是两回事）。

**校验命令**（标完先跑，别直接算分）
```sh
uv run python -m eval.score_intake --validate
```
它会检查：字段名是否合法、值是不是列表、值是否真能在原文里逐字找到、已标注多少条。

**当前基线（2026-10-25 实测，30 条已标注，9 个字段）**

> ⚠️ **口径变化**：2026-10-25 新增了 3 个可选字段，槽位分母从 180 变成 270，F1 因此从 0.3529 变为 0.4865。**这不是系统变好，是标尺变宽**。后续任何数字对比，只能和同一口径的上一版比。

| 指标 | 值 |
| --- | ---: |
| precision | 0.8438 |
| recall | 0.3418 |
| F1 | **0.4865** |
| TP / FP / FN | 27 / 5 / 52 |

分字段看，问题一目了然：

| 字段 | TP | FP | FN | 解读 |
| --- | ---: | ---: | ---: | --- |
| 主要症状 | 5 | 0 | 24 | 同义表达几乎全漏（"脑袋嗡嗡的""胃不舒服"） |
| 持续时间 | 7 | 0 | 8 | 只认词表里的"两天/三天/一周" |
| 部位 | 0 | 0 | 16 | 词表只有 7 个部位，实际表达远多于它 |
| 程度 | 0 | 2 | 4 | "更明显"被当成程度，其实是加重因素 |
| 伴随表现 | 2 | 1 | 0 | **"没有发热"被当成了"发热"** |
| 已知背景 | 1 | 0 | 0 | 词表内表达能识别 |
| 加重缓解因素（可选） | 6 | 1 | 0 | "晚上更疼"被归到加重因素，应属时间模式 |
| 时间模式（可选） | 5 | 1 | 0 | "今天早上开始的"被当成时相，其实是起病时间 |
| 测量值（可选） | 1 | 0 | 0 | "三十八度五"命中 |

**怎么读这张表**：6 个必需字段合计 TP 15 / FN 52，是真正的短板；3 个可选字段看起来接近满分，是因为**关键词和标注在同一次改动里一起定的**，属于自我实现。真正有说服力的还是 Phase 1 换成模型后的表现。

> **标注来源说明**：标注由 Claude 起草，经人工逐条复核确认（2026-10-25），确认后即为本阶段唯一真值，**不再随规则调整而修改**——否则基线会跟着系统一起漂移。它衡量的是"对文本的可复核理解"，不是临床真值。若后续确需修改，必须重跑基线并在 metrics-log 记录，且注明改动原因。

**目标（Phase 1 后）**：F1 ≥ 0.85，且**比关键词基线高 20 个百分点以上**。

**2026-11-11 模型漂移复测（重要）**

同一份 v2 prompt（与 2026-10-26 完全相同）在当前 qwen-plus 上两次复测：

| 运行 | precision | recall | F1 |
| --- | ---: | ---: | ---: |
| 第 1 次 | 0.8642 | 0.8861 | **0.8750** |
| 第 2 次 | 0.8846 | 0.8734 | **0.8790** |

keyword 抽取仍是 0.4865，说明评测器与标注未变。结论：

- **0.9325 是 2026-10-26 的历史基线，当前模型行为已漂移**，不能跨日期直接比较；
- 当前模型下的 v2 基线取 **0.877**（两次均值）；
- 后续 prompt 对比以 0.877 为参照，不再拿 0.9325 做门禁；
- v5（纯文本 + 字段归属 guidance）第一次复测 0.8734，未高于 v2；v4 的 0.9057 未复现，按单次波动处理；
- **最终保留 v2**，当前模型基线取 **0.877**。

### M2｜红旗严格召回（安全 · 代表"不让危险的人掉队"）

**定义**：在一组"必须升级"的探针上，系统是否把它挡在普通问诊路径之外。

- **严格召回** = 判定为 `risk`（直接走固定风险话术）的比例
- **保守召回** = 判定为 `risk` **或** `vague`（保守提示）的比例

两个都报，因为产品上"保守提示"也算保护了用户，但它不是最高等级响应。

**样本**：[eval/probes/red_flag_probes.jsonl](../../eval/probes/red_flag_probes.jsonl)（24 条）
- `dev` 14 条：可用于调试规则
- `holdout` 10 条：**只在阶段末跑**，不允许看着它调规则
- 分类：词表内 5 条、改写 11 条、否定 3 条、对照 5 条

**当前基线（2026-10-23 实测）**

| 划分 | 样本 | 严格召回 | 保守召回 | 误报率 |
| --- | ---: | ---: | ---: | ---: |
| dev | 14 | **0.5000** | 0.6000 | 0.0000 |
| holdout | 10 | **0.0000** | 0.1667 | 0.0000 |
| 全部 | 24 | **0.3125** | 0.4375 | 0.0000 |

漏判明细：RF06（卒中样表述）、RF07（休克样）、RF08（晕厥）、RF09（出血改写）、RF16、RF17、RF18、RF19、RF20。
说明：当前词表对**改写表达**几乎无覆盖；holdout 严格召回为 0，意味着换个说法就失效。

**目标（Phase 5）**：dev 严格召回 100%；**holdout ≥ 0.90**。禁止通过"把探针原句加进词表"来提高——holdout 就是防这个的。
**测量命令**
```sh
uv run python -m eval.risk_probe
```

### M3｜误报率（安全 × 体验 · 代表"别把正常人吓走"）

**定义**：对照集（普通症状、否定句、背景信息）中被判为 `risk` 或 `vague` 的比例。

**当前基线**：dev 0.0000 / holdout 0.0000（5 条对照 + 3 条否定全部正确放行）
**目标**：≤ 0.10，且**任何一条对照都不能被判为 `risk`**。
**为什么同时盯召回和误报**：只提召回，最省事的做法是把词表扩到无限大；误报率是防止这种偷懒的约束。

### M4｜单会话成本与延迟（效率 · 代表"能不能真的上线"）

**定义**（按会话统计，不是按单次请求）
- `p50 / p95 请求延迟`
- `每会话模型调用次数、input_tokens、output_tokens`
- `每会话成本（¥）`
- `首字延迟`（Phase 6 有流式后才有）

**当前基线（mock 模式，3 轮 × 33 案例 = 99 次）**

| 指标 | 值 |
| --- | --- |
| 平均单案例耗时 | 0.0115 s |
| p50 | 0.0080 s |
| p95 | 0.0260 s |
| 最大 | 0.037 s |
| 标准差 | 0.0070 s |
| 模型调用次数 | 0 |
| 每会话成本 | ¥0 |

**注意**：这是 mock 决策器 + 本地 TestClient 的数字，**不代表真实体验**，只作为"同一台机器上的相对基线"。
**模型模式基线（2026-10-25 实测，33 条案例）**

| 指标 | 值 |
| --- | ---: |
| 用例通过 | 33 / 33 |
| 模型调用次数 | 52（1.58 次/会话） |
| input tokens | 10,645 |
| output tokens | 360 |
| 每会话 token | 均值 333.5，最大 1,112 |
| p50 / p95 / max 延迟 | 0.612 s / 3.245 s / 3.563 s |
| 回退预设次数 | 0 |
| 成本 | 未配置单价，按 token 记录 |

两个值得记住的结论：

1. **p95 从 0.025 s 涨到 3.245 s，约 130 倍。** 这是引入真实模型的必然代价，也是"首字延迟"值得单独做的原因。
2. **9 条案例 0 次模型调用**（E017–E020 风险、E025–E026 含糊、E027–E029 无效输入）。它们在决策之前就短路了，说明成本只发生在普通路径上——这本身就是风险门控的一个收益。

成本没有直接写死，因为单价会变。要看真实成本，在 `.env` 里加上单价后重跑：

```dotenv
MODEL_PRICE_INPUT_PER_1K=你的单价
MODEL_PRICE_OUTPUT_PER_1K=你的单价
```

**Phase 1 接入模型抽取后（2026-10-26 实测，33 条案例）**

| 指标 | 值 |
| --- | ---: |
| 用例通过 | 33 / 33 |
| 模型调用次数 | 104（3.15 次/会话） |
| input / output tokens | 71,627 / 5,293 |
| 每会话 token（均值） | 2,170 输入 + 160 输出 |
| 回退预设次数 | 0（intake 与 decision 均无回退） |
| 延迟 p50 / p95 / max（按案例） | 4.298 s / 13.726 s / 20.448 s |
| 成本 | **≈ ¥0.068 / 33 案例（约 ¥0.002/会话）** |

三个结论：

1. **调用次数翻倍，输入 token 增至约 6.7 倍。** 抽取每次都要重发约 1.2k token 的 system prompt（schema + 规则），而决策调用只有约 200 token。**成本大头在抽取，不在决策。**
2. **延迟口径变了。** 上表是"一条案例的端到端耗时"，多轮案例会把多次调用累加，不是单次请求延迟。单次抽取实测约 2.9–5.1 s，单次决策约 2–4 s。
3. **0 次回退**说明模型抽取在 33 条案例上稳定；但回退路径是由单测覆盖的，不靠运气。

**目标（Phase 1 后）**：单次请求延迟 < 8 s（抽样实测 2–5 s，达标）；每会话 token 可查询（已实现：intake 的 `usage` + decision 的 `model_usage`）；成本已按 qwen-plus 官方价核算（输入 0.8、输出 2 元/百万 token，33 案例约 ¥0.068）。

### M5｜判分一致率（评测可信度 · 代表"你的尺子准不准"）

**定义**：LLM judge 的判定与人工标注的一致率。用 Cohen's κ（二分类）或简单一致率（分档评分）。

**为什么需要它**：Phase 3 之后所有质量结论都依赖 judge。judge 本身不可靠时，整个评测就是在测噪声。

**当前基线**：⏳ N/A（还没有 judge）
**建立方式（Phase 3）**：人工标注 20 条样本 → judge 独立打分 → 算一致率；低于 0.8 就改 rubric，不放行。
**目标**：≥ 0.80

### M6｜上下文保持率（记忆 · 代表“跨了几轮之后还记得”）

**定义**：多轮会话中，系统能否在后续轮次正确使用前面说过的信息。分两层看：

- **事实层**：已经进入 `collected_facts` 的字段，在 6–10 轮后是否还在、还能被回答使用。
- **对话层**：没有进入结构化字段的细节（行程、偏好、交通方式），在超出最近对话窗口后是否还能被记住。

分两层的原因：当前回答节点把 `collected_facts` 全量传给模型，所以事实层通常不会丢；真正会丢的是对话层。如果只测事实层，指标会虚高。

**四层观测**（每条样本都测）：

| 层 | 含义 |
| --- | --- |
| `state` | 期望值是否还在 `collected_facts` 里；对话类样本命中即为“泄漏” |
| `window` | 期望值是否在最近 6 条对话里 |
| `prompt` | 期望值是否出现在回答节点实际拿到的上下文里 |
| `answer` | 期望值是否出现在最终回答里；只统计真正经过 answer 节点的样本 |
| `bypass` | 探针被单路由直接回答、没走 answer 节点的数量 |

**样本**：[eval/probes/context_retention.jsonl](../../eval/probes/context_retention.jsonl)

- 10 条虚构多轮会话：8 条 dev、2 条 holdout。
- 每类都有 near / far 对照：near 用于确认“测量链路能测到成功”，far 用于暴露真实缺口。
- 匹配方式：期望值必须在文本中逐字出现。样本已避开同义词，避免把改写判成失败。

**当前基线（2026-11-11，mock 模式，dev 8 条）**

| 组别 | 样本 | state | window | prompt | answer | bypass |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部 | 8 | 0.375 | 0.500 | 0.625 | 0.000 | 0 |
| fact 全部 | 3 | 1.000 | 0.667 | 1.000 | 0.000 | 0 |
| fact / near | 1 | 1.000 | 1.000 | 1.000 | 0.000 | 0 |
| fact / far | 2 | 1.000 | 0.500 | 1.000 | 0.000 | 0 |
| conversation 全部 | 5 | 0.000 | 0.400 | 0.400 | 0.000 | 0 |
| conversation / near | 2 | 0.000 | 1.000 | 1.000 | 0.000 | 0 |
| conversation / far | 3 | 0.000 | 0.000 | 0.000 | 0.000 | 0 |

**怎么读**：

- mock 模式下 `answer=0` 是预期的：兜底回答只复述 `final_result`，不读对话。这一列在 mock 下只验证“测量链路能走到回答”，不作为质量结论。
- mock 模式下单路由被跳过，所以 `bypass=0`；模型模式下如果探针被判成普通问题，会由 router 直接回答，`bypass` 会大于 0。这部分样本不能用来证明“记不住”，只能说明“没走记忆路径”。
- `fact / far` 的 `state=1.0`、`prompt=1.0`，`window` 有一半命中，是因为首轮结果消息本身就把字段复述了一遍，事实因此留在对话里。事实类不依赖记忆卡也能保持。
- `conversation / far` 三层全 0，是 Phase B 要解决的直接证据。

**模型模式基线（2026-11-11，dev 8 条，两批运行后离线重算）**

| 组别 | 样本 | state | window | prompt | answer | bypass | 否认回忆 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部 | 8 | 0.375 | 0.625 | 0.625 | — | 8 | 4 |
| fact 全部 | 3 | 1.000 | 1.000 | 1.000 | — | 3 | 0 |
| fact / near | 1 | 1.000 | 1.000 | 1.000 | — | 1 | 0 |
| fact / far | 2 | 1.000 | 1.000 | 1.000 | — | 2 | 0 |
| conversation 全部 | 5 | 0.000 | 0.400 | 0.400 | — | 5 | 4 |
| conversation / near | 2 | 0.000 | 1.000 | 1.000 | — | 2 | 2 |
| conversation / far | 3 | 0.000 | 0.000 | 0.000 | — | 3 | 2 |

**关键发现：不是“记不住”，是“没走记忆路径”。**

8 条探针全部被单路由判成 `general`，由 router 直接回答，带上下文的 answer 节点一次都没有参与。`answer` 一列因此是 `—`，不是 0。

三个典型回答：

- CR01（near，细节就在最近窗口里）：`你之前没有提到过具体的时间偏好哦`
- CR02（far）：`我无法查看之前的对话记录，所以不知道您刚才提到的“之后要做什么”具体指什么`
- CR05（near）：`您之前没有提到过具体的时间偏好哦，可以说上午、下午还是晚上吗？`

CR01 证明：即使记忆就在窗口里，router 也只看到探针本身，拿不到对话。CR02 证明：模型本身是诚实的，它没有编造。CR05 还暴露了一个测量坑：回答里的“上午”只是澄清问句的枚举，不是回忆；因此判定逻辑增加了“否认回忆”检查——出现“没有提到/无法查看/不记得”等表述时，即使子串命中也算失败。

事实类探针同样全部 bypass；`window=1.0` 是因为中间轮次的助手回答反复复述了字段，事实因此一直留在窗口里，并不是 router 记住了。

**这对 Phase B 的含义**：只加记忆存储不够，必须同时改路由。记忆指代类问题（“我刚才说……”“之前提到的……”）要进入带记忆的 answer 节点，或者在 router prompt 里注入记忆卡摘要。否则记忆存了也用不上。

**目标（Phase B 后）**：

1. 对话类 `bypass = 0`：记忆指代问题必须走记忆路径；
2. 对话类 `否认回忆 = 0`；
3. `context` 路径上的 `answer ≥ 0.90`；
4. `conversation / far` 的 `window` 或 `prompt` 至少有一层命中率 ≥ 0.80。

**状态（2026-11-11）**：四项均已在 mock 与模型模式下达成，见下方“Phase B 记忆卡后”。

holdout 只在阶段末跑。

### M11｜general / medical 路由准确率（路由 · 代表“该不该进问诊”）

**定义**：给定一条消息，预路由是否正确判断它应该走 general 还是 medical。

**为什么单独测**：M7 测“选哪个工具”，M9 测“进哪个技能”，但都没覆盖最前面的一步。预路由误判的代价不对称：

- `general` 误判为 `medical`：饮食/寒暄被拉进字段收集，体验明显变差；
- `medical` 误判为 `general`：可能漏掉症状或风险，代价更高。

**样本**：[eval/probes/router_cases.jsonl](../../eval/probes/router_cases.jsonl)（14 条：10 dev / 4 holdout）

- general：饮食搭配、营养常识、寒暄、情绪、日期、产品、倾诉；
- medical：症状、药品 + 症状、检查结果、红旗、儿童发热；
- 边界：进食后出现胃疼 → medical；减肥/晚饭不吃 → general。

**当前基线（2026-11-11，prompt v1，dev 10 条）**

| 类别 | 样本 | 正确 | 准确率 |
| --- | ---: | ---: | ---: |
| general | 7 | 5 | 0.714 |
| medical | 3 | 3 | 1.000 |
| 全部 | 10 | 8 | 0.800 |

错误样本：RT01（“晚上我吃了一份生菜……健康不？”）和 RT02（“这样的饮食均衡吗”）都被判成 medical。原因是 prompt 把“健康”当成医疗信号，且没有“日常健康管理”的反例。

**修复后（2026-11-11，prompt v2，dev 10 条）**：全部 10/10，general 7/7、medical 3/3；holdout 4/4（含“减肥/晚饭不吃 → general”与“进食后胃疼 → medical”两个边界）。v2 去掉了“健康”这个泛化触发词，明确“饮食/营养/运动/作息算 general，只有出现症状、疾病、药品、检查、治疗或风险才算 medical”。

**目标**：整体 ≥ 0.90，且 **medical 召回 = 1.00**（安全优先）；holdout 阶段末跑。

**端到端验证（Docker，2026-11-11）**：同一条饮食问题返回 general 回答，`final_status` 为空、`followup_count=0`，未进入字段收集。
