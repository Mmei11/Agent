# 求职演示脚本

> 时长约 4 分钟。只使用页面内置的虚构案例；默认 `USE_MODEL=0`，演示不需要 API Key，也不会产生模型调用费用。请勿录入真实个人或健康信息。

## 录制前准备

在项目根目录准备好运行环境，并在录制前完成以下命令：

```sh
docker compose config
uv run pytest backend/tests/
uv run python -m eval.run_eval
docker compose up --build
```

浏览器打开 <http://localhost:8081>。确认首页显示“仅限虚构病例演示”提示，三个场景卡片都可见。将终端窗口提前打开到项目根目录；关闭包含个人信息的标签页和通知。演示时不展示 `.env`、密钥或本地数据库文件。

## 30 秒项目介绍

我做了一个用于展示 Agent 工程实践的虚构病例工作台。后端用 LangGraph 管理多轮状态，FastAPI 提供接口，React 展示对话与结构化结果。风险规则先于普通决策运行；模型只提出追问、调用工具或结束这几种受限动作，程序再校验并执行。会话保存在 SQLite，33 条固定模拟案例检查工作流、故障退路和会话恢复。评测范围是软件行为，项目不面向真实患者。

## 2 分钟项目介绍

这个项目想解决的是一个状态问题：用户会分几轮补充信息，系统需要记住哪些事实已知、哪些仍缺失、问过哪些问题，以及工具是否已经调用。相比把所有逻辑写成一次性提示词，我用 LangGraph 把流程拆成信息提取、风险检查、动作决策、追问、工具和输出节点，并用 SQLite Checkpointer 恢复会话。

模型只负责提出有限动作。动作名和追问条件由程序校验，工具从注册表白名单中调用；预设风险规则在普通决策前执行，输出也会经过结构与边界检查。FastAPI 承载会话 API，React 页面展示追问进度、已知与待确认信息，以及最终结果。

我用 33 条虚构案例通过真实 API 和 graph 检查风险路径、否定与含糊表达、追问上限、工具故障、结果 schema 和会话恢复。Day 17 的评测发现了 6 条软件行为问题；Day 18 修复后，三次独立 mock 评测均为 33/33。这个数字只说明固定案例的流程断言通过，不衡量医疗准确性，也没有覆盖真实模型质量。接下来的优化重点是运行追踪、真实模型回归评测和公开演示的请求保护。

## 常见面试问题

### 为什么使用 Agent 工作流？

下一步动作取决于跨轮收集的信息、缺失字段、已问问题、拒答状态和工具结果。LangGraph 的显式状态与条件边让这些分支可以检查和复现。规则能确定的边界继续由程序执行。

### 为什么只用一个主 Agent？

当前任务范围有限，主要复杂度来自多轮状态与停止条件，没有需要多个角色协作的独立任务。一个显式状态图更容易追踪节点、验证动作和复现失败；未来只有出现清楚的职责拆分和独立评测收益时，再考虑多 Agent。

### 为什么没有做 RAG、GraphRAG 或微调？

当前功能依靠结构化信息、有限本地规则和受限工具，不需要检索外部知识库。加入向量库、知识图谱或微调会增加部署与评测面，却没有对应的当前需求。

### 怎么衡量追问与工具选择？

固定模拟案例检查是否只问一个问题、是否重复追问、追问是否在三次内停止、是否按预设路径处理风险、是否只调用注册工具，以及工具失败和会话恢复是否符合预期。后续真实模型评测会单独记录动作有效性、规则覆盖、延迟和调用费用。

### 33/33 代表什么？

它代表当前 33 条固定虚构案例的自动化软件流程检查全部通过。评测固定使用 mock 决策器，不调用外部模型；它不证明模型答案质量、医疗准确性或真实场景风险识别能力。

### 当前最重要的限制是什么？

风险与拒答识别依赖有限关键词，不能覆盖所有自然语言表达；真实模型尚未进行重复采样评测。项目只用于本地学习与求职演示，不能作为真实医疗服务使用。
